The six rules

These are the constraints FileMind is built around. Each one is enforced in code, and where it can be, in CI — so a change that would break one fails the build.

1. Never delete permanently

OsAdapter::move_to_trash is the only deletion primitive. A CI lint fails if fs::remove_* appears in the core, agent or CLI crates outside FileMind's own control files.

2. Never mass-move without a manifest

The transaction manager is the only path to the file-system adapter. A manifest is written and fsynced before step one; every step's state is journaled; an interrupted transaction is recovered on the next start.

3. Never overwrite

Moves refuse existing destinations. Chaos tests execute a transaction with a simulated crash at every possible point and assert that every original file exists exactly once afterwards.

4. Never silently rename

Every rename is a visible step in the plan; apply checks the plan's fingerprint against the preview you approved.

5. Never follow unknown links

Symlinks and junctions are recorded and never traversed; anything outside the approved roots is never read or moved.

6. Never touch the OS or app internals

A protected-roots list (system folders, /Applications, ~/Library, .Trash) is applied at the scanner, the planner and the adapter.

Automate mode adds a seventh, procedural rule: an unattended action is allowed only after a week of previews, capped per run, and paused on the first conflict. See Automate mode.
